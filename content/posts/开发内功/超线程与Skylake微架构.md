# 理解 CPU 超线程与 Skylake 微架构

从程序员的视角看，代码通常表现为一行一行顺序执行；但在现代 CPU 内部，这种“顺序执行”更多是一种对外呈现的抽象。真正的执行过程早已不再是简单的“取指、译码、执行、写回”，而是一套围绕预测、乱序、并发、缓存和提交构建起来的复杂流水线系统。

以 Intel Skylake 这类现代乱序超标量核心为例，一个物理核心内部可以被拆成几个关键部分：前端负责取指、预测分支，并把复杂的 x86 指令拆解成微指令；后端负责寄存器重命名、依赖分析和乱序执行窗口维护；执行引擎负责把已经就绪的微指令分发到不同执行端口；内存子系统则通过缓存、TLB、Load Buffer、Store Buffer 等机制尽量隐藏访存延迟。

超线程，或者更准确地说 SMT（Simultaneous Multithreading，同时多线程），正是建立在这套执行体系之上的硬件资源复用技术。它不会复制一个完整核心，也不会额外复制一套 ALU、FPU、缓存和执行端口，而是复制少量架构状态，让操作系统看到多个逻辑 CPU。这样，当一个线程因为 Cache Miss、分支预测失败或长延迟指令暂时无法充分利用执行资源时，另一个线程的指令可以进入同一个物理核心，填补原本会空转的周期。

如果用 Go 语言类比，SMT 和 GMP 调度模型有相似的目标：减少底层执行资源的闲置。当某个 Goroutine 因为 I/O 或系统调用阻塞时，Go 调度器会让 P 继续运行其他就绪 Goroutine；当某个硬件线程暂时无法推进时，SMT 则尝试让另一个硬件线程使用同一物理核心中的空闲资源。二者的层级完全不同：GMP 是运行时调度，SMT 是处理器内部的硬件多线程机制。

## 1. 为什么现代 CPU 不是简单流水线

早期教科书里经常把 CPU 执行过程画成：

```text
Fetch -> Decode -> Execute -> Writeback
```

这对理解基础概念有帮助，但已经不足以描述现代高性能核心。真正的瓶颈在于：CPU 主频再高，也不能保证每个周期都有一条有用指令可以执行。

常见浪费来自几类情况：

1. **数据没准备好**：比如一次 Cache Miss 需要去更远的缓存层级甚至 DRAM 拿数据。
2. **分支方向未知**：遇到 `if/else` 或循环跳转时，CPU 不知道下一步该取哪边代码。
3. **指令之间有依赖**：后一条指令要等前一条结果。
4. **执行资源不均衡**：部分端口高度占用，部分端口暂时空闲。

现代 CPU 的核心目标，就是尽量把这些等待隐藏起来。它会预测、拆分、重命名、乱序、缓存、转发，最终再把结果按程序顺序提交，让软件以为一切仍然是顺序发生的。

## 2. 前端：取指、预测与译码

Skylake 的前端负责为后端持续提供可执行的微指令流。它的核心任务不是“执行计算”，而是解决取哪段代码、如何译码、如何保持流水线不断供的问题。

### 2.1 分支预测：保持流水线供给

程序里有大量分支：

```go
if x > 10 {
    doA()
} else {
    doB()
}
```

CPU 在真正算出 `x > 10` 之前，如果停下来等待结果，流水线就会出现空转。现代 CPU 会提前猜测：分支预测器根据历史行为、跳转模式等信息推测下一条路径，然后把这条路径上的指令提前取入并继续推进流水线。

猜对了，流水线持续前进；猜错了，就需要把错误路径上已经做了一半的工作冲刷掉，重新从正确路径取指。这就是 Pipeline Flush。它的代价通常是多个到几十个周期，具体取决于微架构和分支位置。

### 2.2 Decode：把复杂 x86 指令切成微指令

x86 是 CISC 指令集，一条指令可能很短，也可能长达 15 字节；有的只是简单加法，有的可以同时访问内存并做运算。执行引擎不喜欢这种长短不一、语义复杂的东西，所以前端会把 x86 宏指令翻译成更简单的微指令，也就是 micro-ops，常写作 `uops` 或 `μops`。

例如：

```asm
ADD [Memory], EAX
```

从宏指令角度看，这是一条指令；从 CPU 内部看，它可能拆成：

1. 从内存加载数据；
2. 执行加法；
3. 把结果存回内存。

为了避免循环代码反复译码，Skylake 还有 DSB（Decoded Stream Buffer），可以理解为 `uops` 缓存。热循环如果已经译码过，前端可以直接从 DSB 提供微指令，减少功耗和前端压力。

## 3. 后端：乱序执行的核心

前端把指令变成 `uops` 后，后端开始处理现代 CPU 中最关键的一组问题：哪些指令可以提前执行？哪些指令必须等待？在允许乱序执行之后，如何保证异常、分支失败和最终结果仍然符合顺序语义？

### 3.1 寄存器重命名：消除伪依赖

程序员看到的是架构寄存器，比如 `RAX`、`RBX`。但 Skylake 内部有更多物理寄存器。寄存器重命名的核心思想是：不要让多个逻辑写入都挤在同一个名字上。

看一个例子：

```text
1: RAX = 10
2: RBX = RAX + 5
3: RAX = 20
```

第 2 条依赖第 1 条，这是 RAW（Read After Write）真依赖，无法消除。

但第 1 条和第 3 条都写 `RAX`，这类 WAW（Write After Write）很多时候只是名字冲突。硬件可以把它们映射到不同物理寄存器：

```text
RAX 第一次写入 -> P10
RAX 第二次写入 -> P25
```

这样，第 1 条和第 3 条在物理层面就不再争同一个寄存器。RAT（Register Alias Table，寄存器别名表）维护的就是这种“架构寄存器名 -> 物理寄存器”的动态映射。

这和并发编程里减少共享状态的思路类似：如果两个任务本质上不需要共享同一块状态，就给它们独立的存储位置，冲突自然会减少。

### 3.2 ROB：乱序执行，顺序退休

乱序执行会带来一个严肃问题：如果第 90 条指令先执行完了，但第 5 条分支后来发现预测错了，怎么办？

CPU 不能让错误路径上的结果被操作系统或程序真正看见。解决方案是 ROB（Reorder Buffer，重排序缓冲区）。

ROB 的规则可以概括为：

1. **按程序顺序分配入口**：`uops` 进入后端时，按原始顺序进入 ROB。
2. **允许乱序执行**：谁的数据先准备好，谁先去执行。
3. **只允许顺序退休**：只有队头指令完成且没有异常，才正式提交架构状态。

所以，即使后面的指令已经算完，它们也只是“完成但未退休”。如果前面发生异常或分支预测失败，CPU 可以丢弃后续 ROB 项和临时物理寄存器，恢复到干净状态。

用数据库类比，ROB 很像事务提交日志：内部可以并发做很多工作，但对外可见状态必须按顺序、可回滚地提交。

### 3.3 RS / Scheduler：硬件里的就绪队列

寄存器重命名之后，`uops` 会进入 RS（Reservation Station，保留站）或调度器。这里可以理解为硬件级的等待队列：每条指令都在等待自己的操作数。

一条指令可能长这样：

```text
ADD P20, P10
```

如果 `P10` 的值还没算出来，这条指令就不能发射。等某个执行单元产生了 `P10` 的结果，调度逻辑会唤醒依赖它的指令。指令一旦所有操作数就绪，就开始竞争合适的执行端口。

这和 Go 调度器或事件循环中的“等待事件 -> 被唤醒 -> 进入可运行队列”有相似之处，只是 CPU 把这套机制实现成了硬件电路。

## 4. 执行引擎：多端口超标量执行

Skylake 是超标量核心，意味着它在一个周期内不只尝试执行一条微指令。它有多个执行端口，不同端口连接不同类型的执行单元。

可以粗略理解为：

1. **Port 0/1/5/6**：偏计算，处理整数 ALU、分支、部分向量运算等。
2. **Port 2/3**：偏 Load，负责地址生成和读内存。
3. **Port 4/7**：偏 Store，负责写数据和写地址相关工作。

调度器的工作，就是每个周期从已经就绪的 `uops` 中选择合适的指令，分发到能够处理它们的端口上。端口不是越多越好，因为每增加一个端口，都意味着更复杂的调度、旁路、唤醒和布线成本。

### SIMD / AVX：一条指令处理多份数据

普通 ALU 一次处理一个标量。SIMD（Single Instruction, Multiple Data）则允许一条指令同时处理多份数据。

例如 256 位 YMM 寄存器可以容纳 8 个 32 位整数。一次向量加法，就可以同时完成 8 个整数加法。对图像处理、音视频、科学计算、矩阵运算这类场景，SIMD 是非常关键的吞吐来源。

但 SIMD 并非无条件带来收益。它需要数据布局友好、内存访问连续、对齐良好，并且需要编译器或手写代码能够有效向量化。否则，强大的向量单元也可能无法被充分利用。

## 5. 内存子系统：跨越内存之墙

执行引擎很快，DRAM 很慢。一次主存访问的延迟可能远远超过普通 ALU 指令。如果每次读写都直接访问主存，现代 CPU 的执行端口会长期处于等待状态。

所以 CPU 需要一整套内存子系统来隐藏延迟。

### 5.1 L1 / L2 Cache：离核心最近的缓存

Skylake 每个核心附近有很小但很快的缓存层级：

1. **L1 Data Cache**：容量小，延迟低，优先查它。
2. **L2 Cache**：容量更大，延迟更高，L1 Miss 后继续查它。
3. **LLC / L3 Cache**：通常被多个核心共享，再往后才是 DRAM。

缓存依赖两个基本规律：

1. **时间局部性**：刚访问过的数据，可能很快还会访问。
2. **空间局部性**：访问某个地址时，附近地址也可能很快被访问。

这和软件里的本地缓存、Redis、数据库分层很像。区别是 CPU 缓存由硬件自动维护，粒度通常是 Cache Line，而不是业务对象。

### 5.2 TLB：缓存虚拟地址到物理地址的翻译

用户程序看到的是虚拟地址，真正的内存硬件使用的是物理地址。每次访存都需要地址翻译，而完整页表查询本身又需要访问内存。

TLB（Translation Lookaside Buffer）就是页表映射的高速缓存。TLB 命中时，虚拟地址可以很快翻译成物理地址；TLB Miss 时，CPU 需要走页表遍历，代价明显更高。

所以在高性能程序里，连续内存访问、减少随机访问、使用大页等优化，本质上都可能改善缓存和 TLB 行为。

### 5.3 Load Buffer / Store Buffer：把内存读写也做成异步

内存读写不一定能立刻完成。为了减少执行引擎等待，CPU 使用 Load Buffer 和 Store Buffer 管理在途内存操作。

写内存时，执行单元可以先把写请求放入 Store Buffer，然后继续执行后续指令。Store Buffer 后台再把数据写入缓存层级。

但这会产生一个问题：

```text
a = 10
b = a + 5
```

如果 `a = 10` 还在 Store Buffer 里，后面的 Load 去 L1 读 `a`，可能读到旧值。为了解决这个问题，CPU 会做 Store Forwarding：后续 Load 如果命中前面未提交的 Store，可以直接从 Store Buffer 获取新值。

这和软件里的异步写入有点像，但 CPU 必须额外保证同一线程视角下的内存语义正确。

## 6. 超线程 SMT：为什么一个核心能变成两个逻辑 CPU

理解完前面的执行结构后，SMT 的收益来源就比较清晰了。

一个物理核心里有很多昂贵资源：

1. 前端取指与译码资源；
2. 乱序执行窗口；
3. 执行端口；
4. ALU / FPU / SIMD 单元；
5. L1 / L2 缓存和 TLB；
6. Load / Store Buffer。

单线程运行时，这些资源经常无法被完全利用。比如线程 A 遇到 Cache Miss，部分执行单元会等待数据返回；线程 A 遇到长延迟除法或较长依赖链时，其他端口也可能暂时空闲。

SMT 的做法不是再造一个完整核心，而是复制一份或多份架构状态。Intel 对 Hyper-Threading 的说明里明确提到，两个逻辑处理器共享执行资源，而每个逻辑处理器有自己的架构状态，包括通用寄存器、控制寄存器、APIC 寄存器以及部分机器状态寄存器。

这带来两个效果：

1. 操作系统看到的是两个逻辑 CPU，可以把两个线程调度上来。
2. 硬件可以在同一个物理核心内交错处理两个线程的 `uops`，用一个线程填补另一个线程造成的空洞。

这就是 SMT 的收益来源：不是把算力翻倍，而是提高共享执行资源的利用率。

## 7. SMT 与 Go GMP 的类比边界

把 SMT 类比成 Go GMP 是很有帮助的：

1. `Goroutine` 像软件任务流；
2. `P` 像可运行队列和调度资源；
3. `M` 像真正承载执行的操作系统线程；
4. 当某个 G 阻塞时，Go 调度器尽量让别的 G 继续跑，避免资源闲置。

SMT 的思想也类似：当线程 A 无法充分利用物理核心时，让线程 B 的指令进入同一个核心，提升整体资源利用率。

但两者不能混为一谈：

1. Go GMP 是软件运行时调度，SMT 是硬件线程级并行。
2. Go 的切换涉及运行时、栈、M/P/G 状态，SMT 的两个逻辑线程同时驻留在同一个物理核心里。
3. GMP 调度的是 Goroutine，SMT 调度的是来自不同硬件线程的指令流和微指令。
4. GMP 更关注阻塞、抢占、系统调用、网络轮询；SMT 更关注执行端口、缓存 Miss、依赖链和硬件资源利用率。

所以，一个更准确的总结是：

> Go GMP 通过软件调度减少线程和 CPU 的空转；SMT 通过硬件多线程减少物理核心内部执行资源的空转。

## 8. SMT 并不总是更快

SMT 的收益取决于两个线程是否互补。

如果线程 A 经常等待内存，线程 B 有很多可执行计算，那么 SMT 可能明显提升吞吐。如果两个线程都在密集使用同一类资源，比如都在压满 AVX、都在打满 L1 带宽、都在争同一组执行端口，那么 SMT 可能收益很低，甚至因为缓存、TLB、分支预测结构和执行资源竞争导致性能下降。

这也是为什么高性能服务经常需要实测：

1. 对吞吐型 Web 服务，SMT 往往有帮助。
2. 对内存延迟敏感但资源互补的任务，SMT 可能有帮助。
3. 对重 AVX、HPC、低延迟交易、实时任务，SMT 可能需要关闭或做 CPU 绑核隔离。
4. 对 Go 服务，`GOMAXPROCS` 设置到逻辑 CPU 数不一定总是最优，还是要结合 pprof、perf、延迟分位数和实际负载压测。

## 9. 一句话总结

现代 CPU 的核心思路是：把顺序代码拆成大量可调度的微指令，在硬件内部尽可能乱序、并发、预测、缓存和转发，最后再按顺序提交结果。

SMT 则是在这个基础上引入另一条硬件线程流：它复制少量架构状态，让两个逻辑线程共享一个物理核心的昂贵执行资源，用另一个线程的可运行指令填补当前线程留下的流水线气泡。

它不是“一个核心变两个核心”，而是“一个核心尽量少闲着”。
