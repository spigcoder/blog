# 互联网基础架构笔记：DNS、LVS 与 MySQL 高可用

这是我阅读《亿级流量网站架构核心技术》相关内容时的一份整理笔记，主题是流量入口和数据层的两条主线：请求怎么被解析、转发到后端服务，以及数据库如何在主节点故障时保住数据不丢。文中的判断带有我自己的理解，不一定完全准确，更多是把知识点串成一条能自洽的逻辑链。

## DNS 与 HTTPDNS 的适用边界

普通域名解析走的是本地 DNS：客户端把域名交给运营商的 LocalDNS，由它按 根域名服务器 → 顶级域 → 权威域名服务器 的顺序完成递归解析。问题在于这条链路上的每一跳都可能被缓存污染或被运营商劫持，而客户端对结果几乎没有控制权。

HTTPDNS 的思路是绕开 LocalDNS，直接用 HTTP 请求去问自建的解析服务，拿到 IP 后再自己发起连接。这样能规避劫持、能做更精细的调度（比如按客户端归属选就近机房）。

但它有一个明确的使用边界：**只适合移动端 App 和小程序这类能自己控制网络栈的场景**。浏览器环境下拿不到"先解析、再用 IP 建连"的能力，输入域名后浏览器就会走本地 DNS 的递归解析流程，HTTPDNS 插不进去。

## LVS 的四种转发模式

LVS 工作在四层，做的事情是把到达 VIP 的请求分发给后端的一组 RS。几个术语先约定一下：CIP 是客户端 IP，VIP 是对外暴露的虚拟 IP，DIP 是 LVS 与内网通信的 IP，RIP 是真实服务器 IP。

四种模式的差别，本质上就是"改包的哪一层、改几次"，而这个选择直接决定了部署约束和性能上限。

### NAT

NAT 模式下 LVS 必须作为 RS 的网关。

![LVS NAT 模式的数据流向](/assets/posts/源码分析-互联网基础架构-lvs-nat.png)

请求到达 VIP 后，LVS 把目的地址改写为 RIP 并转发给 RS；RS 处理完直接响应，此时响应包的源 IP 是 RIP，但因为 LVS 是 RS 的网关，这个包会被 LVS 拦下，把源 IP 改回 VIP 再交给客户端。

它的代价很明确：

- RS 和 LVS 必须处于同一个局域网，且 LVS 必须是 RS 的网关，部署上不灵活；
- 请求和响应都要经过 LVS 改写，而响应流量通常远大于请求流量，LVS 的带宽会先成为整个集群的瓶颈。

### FULL NAT

FULL NAT 和 NAT 几乎是同一套做法，只是多做了一次源 IP 转换。

![LVS FULL NAT 模式在 NAT 基础上额外转换源 IP](/assets/posts/源码分析-互联网基础架构-lvs-fullnat.png)

除了把目的 IP 改成 RIP，它还会把源 IP 改成 DIP。好处是 LVS 不再需要强制充当 RS 的网关，因为 RS 看到的源地址就是 DIP，响应自然会回到 LVS，跨网段部署也就可行了。

不足同样明显：客户端的真实 IP 在这一步被丢掉了。对于需要基于 CIP 做风控、限流、地域统计的业务，这是不可接受的，通常得靠七层再把真实 IP 透传下去。

### TUN（IP 隧道）

TUN 模式更像是"包裹运输"：请求到达 LVS 后不修改原始报文，而是在外面再套一层 IP 头，外层源 IP 为 DIP、目的 IP 为 RIP，然后转发出去。

![LVS TUN 模式通过 IP 隧道封装转发请求](/assets/posts/源码分析-互联网基础架构-lvs-tun.png)

RS 收到后拆开外层封装，看到内层的目的 IP 是 VIP，所以 RS 需要在 lo 网卡上配置 VIP —— 用 lo 是因为它不会响应 ARP 请求，不会和 LVS 争抢同一个 VIP 的归属。处理完成后 RS 直接以 VIP 为源、CIP 为目的把响应发回客户端。

关键收益在于：**LVS 只转发请求，不转发响应**。响应流量不再穿过 LVS，性能上限比 NAT 高一个量级。

### DR

DR 模式和 TUN 的整体思路一致，区别在改写的层次：TUN 是在 IP 之上再封一层 IP，DR 则是直接改二层的 MAC 地址。

![LVS DR 模式通过改写 MAC 地址转发](/assets/posts/源码分析-互联网基础架构-lvs-dr.png)

数据包到达 LVS 后，目的 MAC 被改成选中 RS 的 MAC，IP 层完全不动；RS 的 lo 网卡上绑定了 VIP，所以它认为这个包是发给自己的，处理后同样直接响应给 CIP。

因为省掉了封装/解封装的开销，DR 是四种模式里性能最好的，代价是 LVS 和 RS 必须在同一个二层网络内。

## LVS 自身的高可用与横向扩展

### 高可用：Keepalived + VIP 漂移

单台 LVS 显然谈不上可用性。典型做法是 Keepalived + VIP：Keepalived 作为守护进程，让多台 LVS 组成一个虚拟组，对外只暴露一个 VIP。正常状态下 Master 持有 VIP 并处理流量，同时周期性地向 Slave 发送心跳。

当 Slave 在一段时间内收不到心跳，就会接管 VIP，并主动广播 ARP，告诉同一局域网内的设备：以后发往这个 VIP 的数据，请送到我的 MAC 地址。切换过程对客户端是透明的，因为 VIP 没有变，变的只是它背后的 MAC。

### 高并发：用 DNS 在 LVS 之上再做一层负载

高可用解决的是"挂了怎么办"，高并发解决的是"一台不够怎么办"。Nginx 的扩展方式是前面放一台 LVS、后面挂多台 Nginx；LVS 的扩展方式类似，只不过它前面那一层是 DNS —— 同一个域名解析出多个 VIP，由 DNS 的负载均衡策略把客户端分散到多台 LVS 上。

![DNS 解析多个 VIP，LVS 与 Nginx 逐层分发到后端服务](/assets/posts/源码分析-互联网基础架构-lvs-nginx-cluster.png)

这样就形成了 DNS → LVS → Nginx → 业务服务 的完整分发链路，每一层都能独立横向扩展。

## MySQL 主从同步

我最近在做 Flink CDC，本质上也是一种基于 binlog 的同步方案，正好拿来和 MySQL 原生的主从复制做个对比。

### 先看 Flink CDC 的全量阶段：无锁快照 + binlog 修正

Flink CDC 的全量同步会按并行度切分数据。比如并行度是 4、总共 1000 条数据，那么每个 task 大致负责 250 条。每个 chunk 的读取过程是这样的：

1. 记录低水位 `W_low`，即当前 binlog 位点；
2. 执行 `SELECT * FROM t WHERE id BETWEEN 1 AND 8096`，短事务，读完立即提交；
3. 记录高水位 `W_high`，即此刻的 binlog 位点；
4. 读取 `[W_low, W_high)` 区间的 binlog，用它来修正第 2 步的快照结果。

为什么需要第 4 步的修正？因为第 2 步不加锁，读取过程中数据随时可能被业务改动：

```text
第②步开始时： id=100, name='Alice'
第②步读到：   id=100, name='Alice'            ← 快照里是 Alice
读取过程中：   业务 UPDATE id=100 → name='Bob'  ← 这条变更进了 binlog
第②步结束
```

此时快照结果里 id=100 是 Alice，而数据库里实际已经是 Bob，两边不一致。修正逻辑就是扫 `[W_low, W_high)` 的 binlog，发现这条 UPDATE 后把快照结果覆盖掉：

```text
修正前的 chunk 结果： [ ..., (100, Alice), ... ]
binlog 里的变更：     UPDATE id=100 SET name='Bob'
修正后的 chunk 结果： [ ..., (100, Bob),   ... ]
```

用"低水位 + 无锁快照 + 高水位 + binlog 回放"这四步，换来了全量阶段不锁表，这是它比传统全量导入更实用的地方。

### 再看 MySQL 原生复制：异步带来的数据丢失风险

MySQL 的主从同步同样分全量和增量。之所以需要全量，是因为 binlog 有保留期限，一个新库接入时如果所需的 binlog 已经被清理，就只能先全量拉一份数据再接着增量同步。

增量的链路是：Master 为每个 Slave 启一个 dump 线程，把 binlog 推给 Slave；Slave 先落到 relay log，再由回放线程从 relay log 执行到自己的数据库。

这里有一个很关键的问题：**这个过程默认是异步的**。Slave 有没有收到 binlog、回放有没有执行失败，Master 并不感知，它写完自己的 binlog 就直接给客户端返回成功了。于是就存在一种很糟的组合：同步实际上已经落后或失败，此时 Master 宕机并触发主从切换，那部分没同步过去的数据就丢了。而在我的理解里，数据都丢了也就谈不上高可用了 —— 高可用不能只保证"有节点能响应"，还得保证响应的数据是对的。

半同步复制就是为了缓解这一点：Master 提交前至少要等一个 Slave 确认收到 binlog，用一点延迟换取"至少有一个从库数据是齐的"。

### 级联复制：缓解复制风暴

当一个 Master 挂了很多 Slave 时，它要为每个 Slave 维护 dump 线程并重复发送同样的 binlog，网络和 CPU 开销随从库数量线性增长，也就是所谓的复制风暴。

![级联复制：让部分 Slave 从上一级 Slave 拉取数据](/assets/posts/源码分析-互联网基础架构-mysql-cascade-replication.png)

做法是把复制关系做成树形：一部分 Slave 不直接连 Master，而是从上一级 Slave 拉数据。Master 的出口压力被分摊了，代价是链路变长、末端 Slave 的延迟更大。

## MHA：尽最大努力不丢数据

![MHA 架构：Manager 管理多组 MySQL 主从集群，每个节点部署 MHA Node](/assets/posts/源码分析-互联网基础架构-mysql-mha.png)

上图是 MHA 的架构。Manager 通过心跳检测 Master 是否存活，这属于基础能力；我觉得真正精彩的是它在切换时为了不丢数据所做的那些补偿动作。

首先，它会选择数据最新、同步最多的 Slave 作为新的 Master。

然后，MHA Node 会尝试通过 SSH 访问原 Master 所在的服务器：

- 如果网络可达，MHA Node 就能读到原 Master 的 binlog。它会拿 Slave 的数据和 Master 的 binlog 做对比，如果发现 Slave 落后，就把这部分差异数据主动补到 Slave 上，让主从数据保持一致；
- 如果网络不可达，就退一步，对比各个 Slave 之间的 relay log 差异，做 Slave 之间的互补。

"选最新的 Slave 当 Master"、"从原 Master 的 binlog 里补齐未复制的数据"、"Slave 之间互相补数据"，这几个策略的目标是同一个：最大程度保证主从切换后不丢数据。

如果把 MHA 和半同步复制一起使用，风险还能进一步降低。因为半同步模式下必然存在一个数据与 Master 一致的 Slave，而 MHA 的选主逻辑正好会挑中它。

## MGR：用一致性换可用性

MGR（MySQL Group Replication）可以理解成 MySQL 自己实现了一套类似 Raft 的数据同步机制。它基于 Paxos 做组内共识，事务提交前要经过复制组内超过半数节点的决议（certify）才算通过，因此至少需要 3 个节点组成复制组；只要宕机节点不超过半数，集群就能继续提供服务，并且支持单主和多主两种模式。

相比"异步复制 + 外部切换工具"这条路线，MGR 是把一致性放到了提交路径上，用写入延迟和可用性的一部分，换来了数据一致性的强保证。这也是我对这几种方案取舍的整体感受：从异步复制到半同步、再到 MHA 补偿、最后到 MGR 共识，本质上都是在"性能"和"不丢数据"之间挪动那条线，没有哪一种是免费的。
